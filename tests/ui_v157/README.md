## item 1：厂商拒了要说出来

用户原话：「**现在 user1@example.com 这个账号依然是卡住的，任何操作都会引起
页面不响应**」。

查下来**不是**页面坏了，也不是这个对话坏了：

1. 这个账号配的是智谱，那把 Key 的余额是 0。厂商对**每一次**调用都回
   `HTTP 429：余额不足或无可用资源包,请充值。`
2. 平台收到这个错之后走的是 `dsapp_ctx_error_advice()` —— 这个函数**只认
   「上下文超出模型窗口」那一类**，对不上就返回 `NULL`。
3. 于是 `ctx_err` 是 `NULL` → **不弹通知、不落库、不留痕**。用户消息躺在对话里
   孤零零一条，后面什么都没有，读起来就是「卡住了」。刷新一下连错误都没了
   （错误原来只活在 `rv$error` 这个服务端内存里）。

同一个时段里 `user11@example.com`（deepseek）的调用是好的 —— 所以是**账号级**的
拒绝，不是平台挂了。这也解释了用户看到的「换一个对话、换一个操作，照样没反应」。

## 三节各管什么

| 节 | 场景 | 断言 |
|---|---|---|
| A 手动模式 | 假 LLM 挂 429「余额不足」，发一条消息 | 8 |
| B 自动执行模式 | 同样的 429，但循环已经跑起来之后才挂上 | 9 |
| C 反面 | 一次**正常**回复，什么都不该多出来 | 5 |

**A**：点完发送**不用再补一条消息**，通知自己弹出来（实测 1.3~1.5 秒）；这一轮
只多了我点发送的那**一条**用户消息（没有为了让错误冒出来而自动补发）；
库里的说明正文含「没能发出去」「余额不足」「请充值」；**刷新之后那条说明还在
页面上**（这正是「一刷新就没」的反面）；出错之后界面回到不忙。

**B**：这一节的关键在**前提**，不在结论。429 必须挂在**第一条请求放行之后**——
不然循环根本起不来（第一轮就死了，测的就不是「循环被停掉」）。
判据是**库里的 tool 消息**（`【执行结果 · 未执行】`，只有循环真的接手并提交过
才会写），不是侧栏那枚「第 N/M 轮」徽章（徽章的观测窗口只有一次 HTTP 往返，
漏了是常态，所以改成事件驱动观察 + 只当辅助）。结论三条：通知弹出来了、
「第 N/M 轮」徽章消失（循环停了）、**这 6 秒里假服务端没收到新请求**（没有偷偷
重试）。

**C**：正常回复**不弹**任何「出错了」的通知、**不往对话里塞**说明。
这一节是「一律报错」的边界：把 `showNotification` 写成无条件却不判 `kind`
的话它会红。

## 这一版探针自己踩的坑

**1. ★★ 「那条说明是新落的」这条断言，第一次红在了一个跟被测代码无关的地方。**
第一版写的是 `mid1 > mid0`（比**出错前那条 assistant** 新）。新账号里压根没有
上一条 assistant，`mid0` 是 `None`，于是 `mid1 > mid0` 恒假 —— 报出来
`出错前 mid=None，现在 mid=2`，看着像「没落库」，其实落了。
改成 **`mid1 > new_ids[0]`**（比**我刚发的那条用户消息**还新）：这个基准在任何
账号上都存在，而且问的正是想问的那件事 —— *不是把某条旧消息又读了一遍*。

**2. ★ 假服务端那个 400 计数器方向是反的（上一版就记过，这次没再踩）。**
`arm_400(msg, times=N)` 数的是**已经拒了几次**，不是「还剩几次」，所以预置
造不出「第一条放行、之后全拒」。做法只能是：先正常发，**看着 `req_n()` 涨到 1**
再挂上 429。

**3. ★★ `probe_model.py` 重载之后不能用 `wait_awake()` 等界面。**
它等的是 `.dsapp-auth`（**登录页**的标记），可重载时 cookie 还在、应用**直接进
主界面** → 那个标记一帧都不出现 → 卡满 150 秒后报「重载之后还是空白」，而屏幕上
早就已经是主界面了，报错指向"应用的界面没了"这个完全无关的方向。用
`probe_v157.relogin()`（它等的是"两种情况里先到的那个"）。
**这条本仓已经记过两次**（`_common.wait_awake` 和 `relogin` 的注释里都写着）——
第三次还是踩了，所以这里也记一条。

**4. ★ 清通知要清干净再进下一节。**
A 节弹的那条 `duration = NULL` 是**不自动消失**的，B 节开始时它还在屏幕上。
每节开头 `clear_notifications()`，否则「B 节弹了没有」永远是真的。

## item 2：切会话不中断 + 多会话并行

改之前 `R/mod_chat.R` 里**一个模块只有一份运行状态**（`st$llm` / `st$acc` /
`st$reason` 就是那一份）。切对话 = 把那一份掐掉，于是"新建一个对话把手上这个
放着跑完"根本做不到，而且切走再切回来会看到**空白**。

现在改成**一个对话一份**：

| 东西 | 是什么 |
|---|---|
| `runs` | `new.env()` 注册表，键是 sid，值是一个 run 环境 |
| `st` | **别名**，永远指向"屏幕上正显示的那一份"。一百多处 `st$xxx` 一个字没改 —— R 的闭包在**调用时**才找自由变量 |
| `use_run(sid)` | 只换显示对象，**不掐任何东西** |
| `show_run()` | 照着这一份**现在的内容**重画（`draft(r$acc)`、思维链游标归零整段重贴）—— 不是清空 |
| 泵 | 每一拍推**所有**活着的 run，只把画面留给 `is_cur = identical(r, st)` 那一个 |

⚠️ **任何改 `rv$session_id` 的地方都必须紧跟着 `use_run(sid)`**，否则 `st` 还
指着上一个对话 —— 那是"往别人的对话里写内容"级别的错，而且**不报错**。

### 这一版在这里挖出的三个真 bug

**1. ★★★ 自动执行循环的起手被自己挡死（P0）。** 循环第一轮时 `a$sid` 还是
`NULL`（它在 `on_llm_done` 的 idle 分支里才写上），而闸门写的是
`identical(as.character(a$sid %||% ""), as.character(r$sid))` → `"" vs "s-…"`
→ 恒 FALSE → **第一次就过不去**，循环根本起不来。判据改成"`a$sid` 是 NULL
**也算我的**"（NULL = 还没认领，不是"别人的"），并且**没有 agent 时仍然挡住**
（不许"没有就放行"）。`selftest.R` 里拿 `.v157b_pick(ex[[i]], "mine")` 从源码里
抠出**真的那个表达式**、在沙箱里跑四种情形，含反例（别的对话那个循环要挡住）。

**2. ★★ 出错说明落进了错的对话。** 写库用的是 `rv$session_id`（屏幕上那个），
而循环属于 `r$sid`。后台那个对话出错时，说明写进了用户正在看的对话里。

### 3. ★★★ 闸门被 R 的**惰性求值**架空（这一版最贵的一个 bug）

前两条是"写错了对象"，这一条是**闸门本身从来没生效过**。

症状：在 A 里发一条 → 切到新建的 C —— **C 的消息区里长出 A 的正文**，
两秒一千多字，一路长到 A 那一轮跑完。切回 A、再切走，照样。

```r
observe({ ... for (r in live) pump_run(r, is_cur = identical(r, st)) })

pump_run <- function(r, is_cur) {
  prev <- st
  st <<- r                    # ← 先把 st 换绑成"正在推的这个"
  ...
  if (is_cur) draft(st$acc)   # ← 到这里**才第一次**求值 is_cur
```

R 的实参是**惰性**的：`identical(r, st)` 在调用那一刻**不求值**，只带着
"在调用者的环境里求值"这个地址传进去。等 `if (is_cur)` 真去求值时，
`st <<- r` 早就执行过了 —— 于是它算的是 `identical(r, r)`，**恒 TRUE**。
"只把画面留给当前那一个"这道闸门，**从写下的第一天起就是空的**。

修法两道，缺一不可：`pump_run()` 第一行 `force(is_cur)`（必须在 `st <<- r`
**之前**），调用点先 `cur <- st` 再进循环（这样那个 promise 求值的对象跟
`st` 再没关系）。

**同一个陷阱的第二个受害者**：`run_notify()` 里的 `identical(r, st)`。
它五个调用点**全都在 `pump_run` 里**，那时 `st` 已经被换绑成 r 了 ——
恒等，于是「后台那个对话出错」要加的那个标题前缀**一次都没加上过**，
用户在 B 里看着、A 那边弹一句没有归属的「余额不足」。判据换成
`r$sid` / `rv$session_id`（和 `dsapp_llm_begin` 里 `cur` 用的是同一对）。

### ★★ 为什么这个 bug 能躲过 3293 条自检 + 三次服务端埋点

两件事叠在一起，缺一件都不会绕这么久：

1. **埋点自己把 bug 藏起来了。** 之前那三次服务端埋点（`show_run` /
   `pump_run` / `output$streaming`）都在函数体**顶部**顺手读了一下
   `is_cur`（`message(sprintf("... is_cur=%s", is_cur))`）—— **读就是
   force**。于是"加了埋点的那份代码里闸门是好的"：日志一路 `is_cur=FALSE`、
   `draft=0`，看上去服务端完全正确。去掉埋点，bug 立刻回来。
   ⚠️ **埋点会改变惰性求值的时机**，这不是第一次坑人（本仓上次是
   `invalidateLater` + 自失效）。要证"某一行没被执行"，只能换一种
   不改求值顺序的手段（这里是直接听 websocket 的帧）。
2. **自检那四条断言传的是字面量。** `pump_run(x, TRUE)` / `pump_run(x, FALSE)`
   在调用前就求好值了，**够不着**惰性这条路。现在补的第 ⑤ 条照调用点的
   **形状**造：同一个环境里放 `st`、实参写 `identical(r, st)` 不预先求值，
   并且先钉一条"这个形状真的是惰性的"当前提。

同一段路还顺手纠正了两个错判：

- `/tmp/probe_lat.py` 量到的"旧正文 0.01 秒就没了"**不算数**：那是在
  **埋点副本**上量的（埋点把 bug 修好了），而且它把终点锚在"消息区里
  找不到旧正文"上 —— 而按下按钮那一刻 A 的第二轮**根本还没开始**，
  它测的是空气。
- `display: contents` 确实是个真坑（shiny 给 `uiOutput` 那层设的，
  `#chat-streaming` 一旦有内容就 `offsetParent === null`、rect 恒 0×0，
  **孩子照常画在屏幕上**，`www/codex.css:337` 记过），**但这一版它不是
  凶手**，只是把我们往"服务端在写 draft"上带偏了一程。
  教训留一条：**"在不在 DOM 里"和"看不看得见"是两件事** ——
  `textContent` 含隐藏子树、`innerText` 只算渲染出来的，判据里两个都要读，
  只读一个就能得出完全相反的结论。

`sprintf("%s 的接口不支持思考模式，故此处不可选。", vlab)`。

`selftest.R` 那条断言**换了形状而且更严**：不再钉"某一句在不在"，而是钉
"灰着那一段里**一个 markdown 记号都不许有**"（`**` 和 `dsapp_md_inline(` 都
不许出现）。只钉某句话的话，下次改文案时这条会绿着失效。

⚠️ 抠那一段源码时**先剥注释**：`strip_comments()` —— 那段说明里就写着 `**`，
不剥的话断言测的是我们自己的注释。

## item 7：页面/会话一断，正在流的那一轮不许丢

线上现场（uid=11，2026-10-01，**连续四轮一模一样**）：`messages` 里 user 那条
在、assistant **一条都没有**；`data/run/` 里连 `.out` 都没留下（而 `.log`/`.err`
在）—— 这个指纹只可能来自 `dsapp_llm_abort()`（全仓只有它同时 unlink 那三个）。

链路：`session$onSessionEnded` → `end_run()` → `dsapp_llm_abort()` → 杀子进程 +
删文件 → **`st$acc` 里已经生成的那几千字，没有任何人写进库**。而同一个文件里
的停止按钮是**存了**的（`paste0(partial, "（已手动停止生成）")`）—— 同一个动作
两种待遇，说明这是漏的。

★★ **真因比上面那层深一级**：整段交接逻辑在响应式上下文**之外**调 `cfg()`。
`cfg()` 是 `dsapp_config_user(state$user_id, ...)`，读的是响应式值；而
`onSessionEnded` 跑在会话**已经拆掉之后** → `Can't access reactive value
'user_id' outside of reactive consumer`。要命的是这条路上**每一处**都包着
`tryCatch` / `try(silent = TRUE)`，于是 full / finish 两档全都静默降级 ——
**V13.7 item 5 那三档「离开页面之后」从来没有生效过**。修法：`isolate(cfg())`
（还有别处的 `isolate()` 取 `user_id`），并且**先存后掐**。

`probe_disc.py`（14 条）和 `selftest.R` 的 item 7 一节都照 item 2 那个套路：
**把回调从源码里抠出来、在全是替身的沙箱里真跑一遍** —— 它跑在会话已拆的当口，
出错没人接，而"存下来了"和"压根没跑"在任何日志里长得一模一样。沙箱里那个
`cfg` 替身**会像真的一样抛**（裸调必抛、包在 `isolate()` 里才给值），这是这一节
真正的闸门。

## item 8：模型被刷新回旧值 —— **跟崩溃没有因果关系**

用户原话：「页面每次崩溃后模型会从我用的 glm4.5 air 被刷新为 glm5.3，你看下
app 崩溃与模型是不是有关系」。

**结论：没有因果关系。** 崩溃只是**顺带触发了一次整页重载**，而重载正是下面
这个窗口出现的时候。不崩、手动刷新，一样会变。

### 两个真相源，发消息用的是**库**

| 存哪 | 谁读它 |
|---|---|
| `users.llm_model` | **发消息用的就是它**（`mod_model.R` 开头的 `saved_model <- s$model`） |
| `user_api_keys(uid, 厂商).model` | 只是**按厂商存的副本**，给切厂商时用 |

线上现场（uid=11）：

```
users.llm_model                 = 'glm-5.3'      ← 权威，但被改成了旧值
user_api_keys(11,'zhipu').model = 'glm-5.3'      ← 副本
用户实际选的                     = 'glm-4.5-air'
```

`glm-5.3` 是 zhipu 静态清单的 `fallback_models[[1]]`（`R/models.R:243`），
`glm-4.5-air` 也在活清单里、**不是**下线模型 —— 所以这不是"没存住"，是
**被改回去了**，而且改它的人正是页面自己的初始化。

### 链条（三段，缺一不可）

1. `observeEvent(input$api_key)`（不防抖那个）把 `model = input$model` 写进
   **钥匙串** —— 用户当时选的是清单头一个（就是 glm-5.3），副本记下了它；
2. 用户改选 glm-4.5-air → 防抖那一拍把 `users.llm_model` 写成 glm-4.5-air，
   但**没有任何人**去改钥匙串那一行 → 两边从此不一致；
3. 下次进设置页，模型下拉**还没把值报上来**（`input$model` 是空串）→ 走兜底
   分支 —— 而那个分支**只问钥匙串、从来不问库** → 读到副本里陈旧的 glm-5.3
   推给控件 → 800ms 后防抖把控件里的值写回 `users.llm_model`。

**库被自己的副本覆盖了。** 崩溃/重载之所以"每次"都撞上，是因为它每次都制造
第 3 步那个"控件还没报值"的窗口。

### 修法

`R/mod_model.R:1331` 那个 `if (!nzchar(cur) || !cur %in% flat)` 兜底块，顺序改成
**库 → 钥匙串 → 清单头一个**，一级比一级弱：

```r
sv <- tryCatch(as.character(dsapp_settings_get(state$user_id,
                                              con = dsapp_db(cfg))$model %||% ""),
               error = function(e) "")
if (nzchar(sv) && sv %in% flat) cur <- sv else { …原来的钥匙串那一支… }
```

⚠️ 不需要另做"厂商对得上吗"的判断：`flat` 本身就是
`dsapp_vendor_model_groups(input$vendor, ...)` 出来的**按厂商**清单，名字在里面
就说明这一家的目录认它。
⚠️ **只在"当前这个名字无效"时才问库**。反过来无条件用库里的值的话，用户在下拉里
选好模型、再点「获取模型」拉活清单时，选择会被弹回上次存的那个 —— 那是 V13.7
item 3 明确修过的、比原 bug 更烦人的一种。这一条有单独的断言钉着。

### 自检怎么验的

照 item 7 那个套路：把 `observeEvent(model_choices(), {...})` 的 **handler 从
AST 里抠出来**，在全是替身的沙箱里**真跑一遍**，看它推给 `updateSelectizeInput`
的 `selected` 是谁。夹具就是线上那个配置：控件空、库 glm-4.5-air、副本 glm-5.3。

| # | 用例 | 期望 |
|---|---|---|
| ① | 控件空 + 库/副本打架 | 推**库**那个，且副本**一次都不许问**（命中即短路） |
| ② | 对照：库为空 | 落到副本 —— 证明 ① 的夹具**不是恒绿** |
| ③ | 库里的名字本厂商目录不认 | 不许硬塞，让给副本 |
| ④ | 库、副本都空 | 退回清单头一个 |
| ⑤ | 控件里的名字**有效** | 原样留着，**库一个字都不许读**（反向那条） |
| ⑥ | 源码顺序 | 兜底块里 `dsapp_settings_get` 在 `dsapp_api_key_recall` 之前 |

**酸测试**（把修法撤掉再跑）：**3 红** —— ① 推出 `[glm-5.3]`（**原样复现线上
症状**）、伴随的"库没被问过"、以及 ⑥；②③④⑤ 照样绿。对照组绿着，说明夹具
有区分度，而不是"无论对错都红/都绿"。

### 这一节自己踩的两个坑（都记在代码注释里了）

**1. ★★ 沙箱里的记录盒子不能叫 `rec`。** handler 里有一句
`rec <- tryCatch(dsapp_api_key_recall(...))`，会在**沙箱那一层**把同名变量覆盖
掉 → `.v158_run` 返回的就不是记录盒子、而是那个 list → `r$sel` 静默变 `NULL`。
要命的是**只有走到 else 分支的用例会露出来**（走库那一支没有这句赋值），所以
症状是"同一个夹具有的绿有的红"。第一次跑 4 条红，其中 3 条是这个。改名 `.REC`
就好了。

**2. ★★ ⑥ 的判据第一次指错了地方。** 全文件第一处
`dsapp_api_key_recall(state$user_id` 在 **1175 行**，那是**另一个** observer
（base_url 兜底，V13.12），位置在兜底块**前面** —— 不圈窗口的话 `regexpr`
拿到的就是它，于是"副本"的坐标落在"库"前面，**修好了也照样红**。改成先在
`if (!nzchar(cur) || !cur %in% flat) {` 上开 1200 字的窗口再找。

（顺带：这一节自己那条 ① 的伴随断言第一版也写错了 —— 写成"两个来源**都**问过"，
而库那一支命中就短路，副本本来就**不该**被问。是 4 条红里的第 4 条。）
