## ③ 为什么单列一节：这一版自己修掉的那个回归

「上下文」和「单次输出」指向的是**同一个值**（`state$ctx_limit`：一个数同时
管"喂进去多少"和"能回多长"）。用户选的就是这个形态，但它在界面上有个必然的
后果：**这两个勾不能各自独立**。

第一版把它写成了

```r
want <- isTRUE(input$unlim_maxtok) || isTRUE(input$unlim_ctx)
```

于是"只取消其中一个"算出来的 `want` 还是 `TRUE` —— **那一次点击什么都改不了**。
而屏幕上：那个框已经空了、取消勾选该出现的数字框也冒出来了。用户以为收紧了，
其实 `state$ctx_limit` 一个字节都没动。（改成 `apply_unlim_pair()`：两个勾
分别触发，但都去写**同一对**，判据是"现在到底是不是不设上限"而不是"哪个勾被点了"。）

⚠️ 这种事**只有浏览器能抓到**：`selftest.R` 里 grep 到的是那几行源码，
`||` 那版和 `apply_unlim_pair` 那版**grep 出来一样长**。

## ④ 为什么要来回两趟

对话页和模型服务页是**两个模块**，各有一份控件。它俩之间的通道是
`state$maxtok_cmd`（对话页写指令 → 模型页收），而反向只能靠
`state$ctx_limit` 变了之后把对话页那个框**拨回去**（`ctx_settled`，
1.5 秒防抖）。

两条路都得量，因为断任何一条的表现都是"两边各说各话"，而**用户只看得见
自己面前那一个**：

* 只量正向（对话页 → 模型页）会漏掉"对话页那个框永远显示一个过期的数"；
* 只量反向会漏掉"设了根本不生效"。

反向那条要等**防抖**（1.5 秒）+ 一个 Shiny 来回，所以轮询上限给到 25 秒 ——
5 秒的时候报"没拨回来"是假红。

## ★★ ④ 抓到的那个真 bug：陈旧回发（2026-10-04 已修）

第一版 ④ 在这个断言上红了两轮：

```
✗ 往回勾的时候两个勾没一起亮
   DOM #chat-unlim_ctx = False   input$chat-unlim_ctx = False   （点完 10 秒）
```

光看这一行分不出两种可能：**这一击没落到 input 上**，还是**落上了又被谁按回去**。
`click_trace()` 逐拍量了一次，形状立刻清楚了：

```
+0    ms DOM=True  input$=True     ← 点到了，客户端也报上去了
+150  ms DOM=False input$=False    ← 150 毫秒内被服务端按了回去
```

服务端那侧的 TRACE（把那几条 `message()` 打进实例副本的 `app.log`）给出了次序：

```
TRACE pair want=TRUE                       ← 用户把勾点回来
TRACE set_maxtok 0                         ← 对话页发指令：不设上限
TRACE recv v=0 rv$maxtok=49152             ← 模型页收到
TRACE apply_ctx_limit want=0               ← ① 真相写对了
TRACE bigobserve in.max_tokens=49152 rv=0  ← ② 紧接着它重跑，读的是**旧值**
TRACE apply_ctx_limit want=49152           ← ③ 真相被盖回去
TRACE push unlim=FALSE                     ← ④ 两个勾被按回"灭"
```

起因：`updateNumericInput()` 只把消息**发给浏览器**，服务端手里的
`input$max_tokens` 要等浏览器回发才会变 —— 那是**下一个来回**的事。中间只要
模型页那个 `observe()` 因为任何别的原因重跑一次，它读到的就是这一格被取代的
旧值，于是按旧值写一遍真相，把刚下的指令当场撤销。

⚠️ 两个"看起来能挡"的东西都挡不住它：

* `syncing` 闸只管得住**同一拍**里的回发，而这个值是从浏览器绕了一圈回来的；
* **两边各自都对**（接收端算得对、公式也对），错的是**次序** —— 所以
  `selftest.R` 里那些源码断言全绿，只有浏览器抓得到。

修法（`R/mod_model.R`）：接收端在改 `rv$maxtok` **之前**把"这一格现在写的还是
它"记进 `maxtok_stale`；写真相那一处读到它就改用 `rv$maxtok`，这一格真报上
新值（或被清空）之后守卫自动撤销。比较走 `all.equal` —— `identical(49152L, 49152)`
是 `FALSE`，那样守卫永远不生效，而症状和没修一模一样。

> 这一条现在是**回归测试**：`selftest.R` 钉源码（名字 / 次序 / `<<-` / 比较方式），
> 本目录 ④ 钉行为。缺一边都不够 —— 源码对而行为错是接线没生效，行为对而源码错
> 是改到别处去了、下一版会被重构掉。

## 踩过的坑（写在这里，免得下一个人重新踩）

* ★ **通知会盖在控件上。** 默认那一组就是"全都不设上限"，所以第一次进对话页
  **必弹**一条，它压在右下角 —— 不关掉的话点勾选框报的是
  「`intercepts pointer events`」，**报错指向的是那个勾本身**，看不出是通知。
  每处 click 之前 `clear_notes()`。（和那个首选项弹窗同一类坑：
  `first-run-onboarding-modal-blocks-clicks`。）
* ★ **数字不写死。** 3 / 2 / 8.5 这三个数这一版刚动过（自动修默认从"3 次"变成
  "不设上限"，时长滑块加了"再高一格"那一档）。探针里的 `rnum()` 从
  `R/config.R`、`R/models.R` 现抠，抠不到 / 算不出来 / 同名常量两份定义
  **一律 `sys.exit`** —— 不猜。写死数字的话，下一个版本里探针会拿旧数去比新
  代码，报出来的错指向完全无关的地方（`constant-change-leaves-stale-literals`）。
* **`fill()` 不等于"报上去了"。** Shiny 的 numeric 绑定还要一个 change
  （失焦）才发消息。`set_num()` 里那句 `keyboard.press("Tab")` 是必须的 ——
  少了它服务端什么都没收到，而下游看起来就是"我填了但它没生效"。
* **"在 DOM 里"≠"出现了"。** 就地出现的那三个控件是 `renderUI` 画的：
  没勾的时候**连节点都没有**。所以判"没出现"要看 `exists()`，判"出现了"要
  `exists()` **和** 矩形非零（`seen()`）—— 隐藏元素的矩形是全 0，光看节点
  会把"被 display:none 掉"当成"出现了"（`hidden-element-has-zero-rect`）。
* **滑块的值得走它自己的实例。** ionRangeSlider 把原来的 `<input>` 换掉了，
  读 `el.value` 可能读到旧值。`JS_SLIDER` 先试
  `jQuery(e).data('ionRangeSlider').result.from`，取不到才退回 `el.value`。
* **`#chat-agent_fix` 和 `#chat-unlim_fix` 是两个东西**，别点错：
  前者是「自动执行」那一格里的**开关**（自动修要不要开），后者才是这一版加的
  「不设上限」里的**次数上限**。同一个页面上两个控件都叫「出错自动修」，
  靠所在的那一组区分。
* **⑥ 要发两条消息。** 第一次发消息弹的是「AI 怎么干活？」那个首选项弹窗 ——
  两条提示**互斥而且弹窗优先**（V16.1 item 5 排的序，见 `mod_chat.R` 那行）。
  只发一条量到的是"没有任何人提醒"，而那是设计如此。探针里第一条只为把弹窗
  用掉，第二条才量那条提醒。
* **点滑块要真的拖。** ionRangeSlider 的手柄自己有宽度，**点轨道最右边**那一下
  算出来的值不一定是 max（实测读到的是初值）。所以 ⑤ 里改成
  `mouse.down()` → `mouse.move(..., steps=12)` → `mouse.up()`，手柄从**这个**
  滑块身上找（`closest('.irs')` 里那个），不是页面上第一个手柄。
* ★★ **手柄的 class 是 `.irs-handle`，不是 `.irs-slider`。** ionRangeSlider
  2.3 起改的名（本机实测 `document.querySelectorAll('.irs-slider').length` = 0）。
  这一条值得单独记：第一版写的是 `.irs-slider` + "找不到就 ⚠️ 跳过"，
  于是这一整条**从来没跑过**，而输出里它和"跑过并通过了"长得一模一样，
  探针照样打印「全绿」。现在**找不到手柄 = 红**。凡是"拿不到元素就跳过"的
  写法，都要先问一句：这个元素上次真的被拿到过吗？
  顺带：拖之前 `scrollIntoView({block:'center'})` —— 元素在视口外时鼠标事件
  **没人接收**，而 `getBoundingClientRect()` 照样返回正数
  （`playwright-drag-below-the-fold`）。
* **量"拖到哪一格"要读它自己的实例**：`jQuery(e).data('ionRangeSlider').result.from`。
  `.irs-line` 的 `getBoundingClientRect()` 就是轨道的两端，`right - 1` 落在最后一格。
* **量"点没点上"要逐拍量。** 见上面 ④ 那段：等 10 秒再看一眼，"
  这一击没生效"和"生效了又被弹回"是**同一个数**。`click_trace()` 在
  0/150/400/1200/3000 ms 各记一次 DOM 和服务端两份状态，`dump_unlim()`
  把那一格的内外两份值一起摊开。
* **调试可以只跑几节**：`V162_SEC=abcd python3 probe_unlim.py`。
  ⚠️ 各节之间**是有状态的**（③④ 以上一节留下的勾选状态为前置），从中间开始跑
  而红，先看是不是跑法不对。

## 探针验不到 / 自检验不到的那一半

`selftest.R` 里那两节扫的是**源码**：它能证明"函数算得对、接线接上了"，
证明不了"用户看得见"。本仓在这上面栽过两次（V13.17 的 `wall_limit`、V14 的
内联 `img` 属性，都是"自检全绿而功能没被验过"），所以这两边的判据**互不替代**：

* 自检管：`dsapp_fix_max_value(NULL)` 回哨兵不是常量、闸门那句报的是**用户设的**
  次数、`state$ctx_limit` **只有一个写入口**、`chk_now` 对四种"没值"的态度、
  `unlim_detail` 里每个 `rv_*` 都 `isolate` 了……
* 探针管：这四个勾真的画出来了、点得动、点完真的变、变了真的走到另一个模块。
