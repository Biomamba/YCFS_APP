# 科研分析规范与 Agent 工作流

来源仓库是一个 Claude Code 的模板/配置集合（900 多个 SKILL.md，绝大多数是 CLI
工具、dashboard、前端模板这类和做分析无关的东西）。这里只留两类内容：**① 科研数据
从探查到成文的一套做法**（数据探查、统计检验、出版级作图、论文/报告写作）；
**② 把多步任务组织成工作流的方法论**（需求澄清、计划、上下文与错误管理、子任务
拆分、怎么写好一条技能/规则）。

## 什么时候按这条技能走

用户丢来数据文件说"看看里面有什么""帮我分析一下" → §1–§2；要出图、要写报告/摘要/
幻灯片 → §3–§4；任务超过三步、要跑很久、要产出多个文件 → 先按 §6 立计划再动手；
用户要把某套做法固化下来（"存成技能""写进规则"）→ 按 §7 写。

## 1. 开工前先探资源，再决定做法

不要在不知道机器有多少内存的情况下 `read_csv` 一个几十 G 的文件。**任何吃资源的
任务开始前，先花一次工具调用把资源摸清楚**，结果落盘成一个文件（例如
`resources.json`），后面所有决策引用它，而不是凭感觉。要探的：

| 项目 | 怎么探 | 影响什么 |
|---|---|---|
| 逻辑核数 | `os.cpu_count()` / `nproc` | 并行 worker 数 |
| 可用内存 | `psutil.virtual_memory().available` | 能不能整表载入 |
| 磁盘可用空间 | `shutil.disk_usage('.')` | 中间文件能不能随便写 |
| GPU | `nvidia-smi` / `rocm-smi` | 要不要走 GPU 路径 |
| 已装包 | `pip list` / `installed.packages()` | 能不能用某个库 |

对应的默认策略（经验值，不是硬规则）：

- **数据集超过可用内存的 50%** 就不要整个读进来：用
  `pandas.read_csv(chunksize=...)` 分块、`dask.dataframe`、或 `zarr`/`h5py`
  做 out-of-core。
- **并行**：8 核以上 `workers = cores - 2`；4–7 核 `cores - 1`；少于 4 核顺序跑，
  别开进程池（调度开销比省下的时间还多）。
- **磁盘充足**（>100 GB）就大胆写中间文件；紧张（<10 GB）就边算边压。
- 把探测结果和"因此我选择了 X"写进报告的 Methods，这是可复现性的一部分。

## 2. 数据探查（EDA）：先描述，再分析

拿到任何文件，**第一步永远是回答"这是什么、长什么样、有没有问题"**，不要直接跳到
做检验。EDA 的产出是一份 Markdown 报告，文件名约定 `<原文件名>_eda_report.md`
（`expr.csv` → `expr_eda_report.md`），和原始数据放同一层。

### 2.1 先识别文件类型，再决定检查什么

按扩展名分流，不要对每个文件都跑同一套 pandas 检查：

- **表格类**（`.csv/.tsv/.xlsx/.parquet`）：行列数、dtype、缺失比例、重复行、
  数值列分布与离群值、类别列取值集合。
- **测序与基因组类**（`.fasta/.fastq/.sam/.bam/.vcf/.bed/.gff/.gtf/.bigwig/
  .h5ad/.loom/.mtx`）：序列条数与长度分布、GC 含量、质量分数分布、比对率与
  覆盖度、变异位点数与质量、矩阵稀疏度与维度。
- **图像与显微**（`.tif/.nd2/.czi/.lif/.dcm/.svs`）：维度（X/Y/Z/通道/时间）、
  位深与值域、通道波长、像素物理尺寸（有没有空间标定）、强度统计。
- **数组与层级**（`.npy/.npz/.h5/.zarr/.mat/.nc/.fits`）：shape、dtype、无效值/
  哨兵值、坐标轴含义。

**大文件一律抽样**：百万行以上先读前 N 行或随机 N 行，并在报告里注明这是抽样。

### 2.2 报告必须有这几节

文件基本信息 → 结构（维度、字段、dtype、单位）→ 质量评估（缺失、重复、离群、
越界、批次信息）→ 关键发现 → **明确写出的下一步建议**（做什么预处理、用什么
检验、配什么图）。最后一条是这份报告存在的理由 —— 没有具体建议的 EDA 等于没做。

### 2.3 编码前的三条纪律

- 先把 dtype 说清楚再算：字符串列里的数字（`"1.2"`）参与运算是静默的坑。
- 分组比较前先点名组别与样本量，`n` 小于 3 的组不要拿去做统计，直接说做不了。
- **写清楚你扔掉了什么**：过滤了多少行/基因、依据是什么。只写剩余数量不写依据，
  等于隐藏了分析者自由度。

## 3. 统计检验：先选对，再跑，最后算效应量

### 3.1 选检验的决策路径

| 情形 | 参数方法 | 非参数替代 |
|---|---|---|
| 两组独立，连续，近似正态 | 独立样本 t 检验 | Mann-Whitney U |
| 两组配对，连续，近似正态 | 配对 t 检验 | Wilcoxon 符号秩 |
| 两组，二分类结局 | 卡方 / Fisher 精确（期望频数 < 5 用 Fisher） | — |
| ≥3 组独立，正态且方差齐 | 单因素 ANOVA | Kruskal-Wallis |
| ≥3 组独立，正态但方差不齐 | Welch ANOVA / Brown-Forsythe | — |
| ≥3 组配对 | 重复测量 ANOVA | Friedman |
| 两连续变量关系 | Pearson（双变量正态） | Spearman / Kendall |
| 连续结局 + 多个预测项 | 多元线性回归 | — |
| 二分类 / 计数 / 生存结局 | Logistic / Poisson（过度离散用负二项）/ Log-rank 或 Cox | — |

**跑之前必须先查假设**（最容易跳过、也最容易出事的一步）：正态性用 Shapiro-Wilk
+ Q-Q 图（按组分别查，不要只查总体）；方差齐性用 Levene + 箱线图；回归看残差 vs
拟合值图；离群值用 IQR 法和 z-score 法各跑一遍并报告差异。

违反了要有明确应对，不要只写"假设不满足"：正态性轻度违反且每组 n > 30 → 参数
检验仍稳健，可以用但要在报告里说明；中度违反 → 换非参数；重度 → 先变换（log /
平方根）或非参数；方差不齐 → t 检验换 Welch、ANOVA 换 Welch/Brown-Forsythe、
回归用稳健标准误；线性不满足 → 加多项式项、变换变量或用 GAM。

### 3.2 一定要给效应量与置信区间

**只报 p 值是半个结果**。p 说"有没有"，效应量说"有多大"，CI 说"有多准"。

| 检验 | 效应量 | 小 / 中 / 大 |
|---|---|---|
| t 检验 | Cohen's d | 0.20 / 0.50 / 0.80 |
| ANOVA | 偏 η² | 0.01 / 0.06 / 0.14 |
| 相关 | r | 0.10 / 0.30 / 0.50 |
| 回归 | R² | 0.02 / 0.13 / 0.26 |
| 卡方 | Cramér's V | 0.07 / 0.21 / 0.35 |

这些只是经验基准，要结合领域语境解释。**功效分析同样容易被滥用**：事前算样本量
是正当的（`tt_ind_solve_power`、`FTestAnovaPower`）；**事后再算"观测到的功效"
没有意义**，等价于用 p 值反推，要报就报灵敏度分析（"以 n=50 在 α=0.05、power=0.8
下能检出 d ≥ X"）。

### 3.3 多重比较与选择偏倚

测了很多个假设就一定要校正（Bonferroni 保守；组学默认 FDR/BH）；把**主结局**和
**探索性子组**分开写 —— 把探索性发现当主结论，是审稿人第一个抓的点；检查 p 值是
不是可疑地堆在 0.05 下面一点点（p-hacking 的典型指纹）。假设先立后验（HARKing）、
结局替换、只报显著结果，都算学术不端，不是"写作技巧"。

### 3.4 报告格式（照抄这个骨架）

t 检验示例：

```
Group A (n = 48, M = 75.2, SD = 8.5) 显著高于 Group B (n = 52, M = 68.3, SD = 9.2)，
t(98) = 3.82, p < .001, d = 0.77, 95% CI [0.36, 1.18]，双尾。正态性（Shapiro-Wilk:
A W = 0.97, p = .18）与方差齐性（Levene F(1, 98) = 1.23, p = .27）均满足。
```

必报项：各组 M/SD/n、检验名与统计量、自由度、**精确 p 值**（不要只写 p<.05）、效应
量及其 CI、假设检验结果、以及所有计划内的分析（**包括不显著的**）。

## 4. 出版级作图

### 4.1 落盘是硬要求

服务器上没有显示器，`plt.show()` / 裸 `print(p)` 等于什么都没产出。**每张图都必须
显式保存**：

```python
fig.savefig('figures/volcano_treat_vs_control.pdf', bbox_inches='tight')  # 矢量
fig.savefig('figures/volcano_treat_vs_control.png', dpi=300, facecolor='white')
```

R 侧同理：`ggsave(file, plot, width, height, dpi = 300, units = "in")`，或者 `pdf()`
/ `png()` 配 `dev.off()` 成对出现。**文件名要能看出画的是什么**，不要 `plot1.pdf`。

### 4.2 格式、分辨率、尺寸

| 图的类型 | 分辨率 | 格式 |
|---|---|---|
| 照片、显微、凝胶 | 300–600 dpi | TIFF / PNG |
| 折线、散点、柱状等线条图 | 600–1200 dpi | PDF / EPS / SVG（矢量优先） |
| 线条 + 图像混合 | 600 dpi | 混合按最高要求取 |

**永远不要用 JPEG 存科学数据**（有损压缩会伪造出数据里不存在的结构）。

常见期刊的单栏/双栏宽度（出图时按这个定 `figsize`）：Nature 系 89 / 183 mm、
Science 55 / 175 mm、Cell 系 85 / 178 mm。不要用 matplotlib 默认的 6.4×4.8 英寸
—— 缩到单栏排版时字会小到读不了。

### 4.3 配色：默认就要色盲友好

- **首选 Okabe-Ito 八色**（对各类色觉障碍都可区分）：
  `#E69F00, #56B4E9, #009E73, #F0E442, #0072B2, #D55E00, #CC79A7, #000000`。
- 连续量用感知均匀的 colormap（`viridis` / `plasma` / `cividis`）；发散量用
  `RdBu` / `PuOr` / `BrBG`，**不要用红绿对比表达上调/下调**。
- **永远不要 `jet` / `rainbow`** —— 它会在数据里造出并不存在的亮带。
- 每张图都要**转成灰度看一眼**，确认不靠颜色也能读。

### 4.4 字体与标注

- 无衬线字体（Arial / Helvetica 系），**字号按最终印刷尺寸给**：轴标签 7–9 pt、
  刻度 6–8 pt、面板字母 8–12 pt 加粗。标签用句首大写、单位放括号里。
- 多面板图：面板字母统一放左上角（Nature 用 a, b, c 小写加粗；Science/Cell 用
  (A), (B), (C)），同一图里所有面板尺寸一致。显微图必须有比例尺。
- 图注必须**自解释**：缩写展开、单位写明、样本量 n 写出、显著性符号含义写清。
- 图表选择：能用一两句话讲清的就别做表；需要精确数值做表；需要看趋势/关系/分布
  做图。

### 4.5 中文环境的额外注意

中文字体不要写死某个本机才有的字体名，不确定时先查
（`systemfonts::match_font()` / `matplotlib.font_manager`），或者直接用英文标签。
默认字体渲染中文会变成方框，而且这个错误在 PDF 里往往到投稿前才被发现。

## 5. 写作与成文交付

### 5.1 结构

论文按 **IMRAD** 走：Introduction（背景→缺口→目标）、Methods（设计、对象、流程、
统计方法）、Results（客观陈述，不解释）、Discussion（解释、对比文献、局限、展望）。

**摘要** 100–250 词，能独立成篇。投稿前按目标期刊的字数卡：Nature 系 ≤ 200 词、
Science ≤ 125 词、PNAS 250 词（另需 120 词 Significance Statement）、
NEJM/Lancet 结构式 250–300 词、PLOS/Frontiers 通常 ≤ 300 词；投稿稿一般单栏、
12 pt、双倍行距。

按研究类型套报告规范：**临床试验 CONSORT、观察性研究 STROBE、系统综述 PRISMA**。
这不是可选项，是审稿和编辑部的硬检查项。

### 5.2 写法

- **正文必须是成段的连贯散文，最终稿里不要出现项目符号。** 两步走：先用要点搭
  每节骨架，再把骨架展开成完整段落。一段一个中心意思，段首句点题。
- 用精确数字代替模糊程度词："seemed to help quite a few patients" →
  "reduced symptoms in 68% (32/47) of patients"。
- 删掉凑字数的短语：due to the fact that → because；in order to → to；
  it is important to note that → 删。名词化动词还回去：make a decision → decide。
- 术语首次出现给定义，代词指代要明确。Methods 里被动语态可以（"Blood samples
  were collected"），Results/Discussion 里主动语态通常更清楚。

### 5.3 引用与文献

- 引用格式跟着期刊走：AMA（上标数字）、Vancouver（方括号数字，生物医学默认）、
  APA（作者-年份）、Chicago、IEEE。**每条引用都要有可核验的标识**（DOI / PMID /
  arXiv ID），并核对元数据与原文一致。不要凭记忆写引用，宁可少写。
- 综述类任务用 PICO 立题（Population / Intervention / Comparison / Outcome），
  检索式**原文记录**：

  ```
  ("CRISPR"[Title] OR "Cas9"[Title]) AND ("sickle cell"[MeSH] OR "SCD"[Title/Abstract])
  AND 2015:2024[Publication Date]   → 命中 247 条
  ```

  记录检索引擎、检索日期、时间范围、命中数，去重按 DOI（没有再用标题），筛选
  过程留痕：初检多少 → 去重后多少 → 标题筛掉多少 → 全文筛掉多少及原因。
- **工作区通常没有外网**：检索不到时不要编造文献，改为把检索式、目标数据库、
  纳排标准整理成一份"待检索清单"交给用户，让他在有网的环境执行。

### 5.4 报告/幻灯片的形态

幻灯片按 **1 分钟 1 张**估量（15 分钟报告 ≈ 15–18 张，结果占 40–50%）。叙事弧：
Hook（30 秒抓注意）→ 背景 → 问题/缺口 → 方法 → **结果（40–50%）** → 意义 → 收尾。
每张结果图都要有一个"所以呢"。图表用代码生成（matplotlib / ggplot / LaTeX），
流程示意图用 mermaid / TikZ / graphviz 这类可复现的方式画，不要依赖需要联网的
外部出图服务。

## 6. 多步任务：先立计划，再动手

适用于任何三步以上的任务。核心心智模型一句话：

> **上下文窗口是内存（易失、有限），文件系统是硬盘（持久、无限）。重要的东西一律落到盘上。**

### 6.1 需求澄清（在写代码之前）

模糊需求（"加个分析""做个图"）先澄清，别猜。按四个维度自查并打分（总分 100）：

| 维度 | 满分 | 检查点 |
|---|---|---|
| 功能清晰度 | 30 | 输入输出明确 10 / 交互方式明确 10 / 成功标准 10 |
| 技术具体性 | 25 | 技术栈 8 / 集成点 8 / 约束 9 |
| 实现完整性 | 25 | 边界情况 8 / 错误处理 9 / 数据校验 8 |
| 业务背景 | 20 | 问题陈述 7 / 目标用户 7 / 成功指标 6 |

规则：**一次只问一类问题，每轮 2–3 个**；分数到 90 以上再动手。已经给了文件路径、
代码片段或明确复现步骤的，不要反过来追问，直接开工。

### 6.2 计划文件

在**工作目录**（不是技能目录、不是 `.claude/`）建三个文件：`task_plan.md`（阶段、
进度、决策，每阶段结束后更新）、`findings.md`（探查发现与数据结论，**有发现就写**）、
`progress.md`（操作日志、命令与报错，全程记）。

计划本身的写法：

- 目标一句话；任务 5–10 条，一条一行动词开头（"过滤…""拟合…""导出…"）。
- **每条任务后面跟 `→ 验证：<怎么确认做完了>`**，验证必须是可执行的动作
  （"`nrow(keep)` 与预期一致""读回 csv 检查行数与列名"），不是"检查是否正确"。
  **最后一步永远是验证**，不要排在中途。计划超过一页说明拆得太细，合并。
- 每完成一条就改 `[x]`，不要凭记忆跟踪。会话被压缩或打断后，先读这三个文件
  恢复状态，再做决定。

### 6.3 上下文与错误的纪律

- **两动作规则**：每做完两次查看/检索类操作，立刻把关键结论写进文件。图片、
  网页、截图这类多模态信息一进上下文就容易被挤掉，转成文字才留得住。
- **大内容写文件，不塞上下文**：中间结果、长日志、大表都落盘，需要时读片段。
- **错误全部记账**（错误 / 第几次 / 怎么处理的），一条不漏。**三次失败协议**：
  第 1 次诊断并针对性修复 → 第 2 次换方法（不同库/不同工具），**绝不原样重试**
  → 第 3 次回到假设层面重新想（是不是前提就错了）→ 三次都不行就停下来找用户，
  说清楚试过什么、具体报错是什么。
- **五问自检**（能答上来就说明上下文管理是健康的）：我在哪（当前阶段）？要去哪
  （剩余阶段）？目标是什么？学到了什么？已经做了什么？

## 7. 拆分、并行与"怎么写一条好技能"

### 7.1 拆任务

- 粒度：一条任务 2–5 分钟、一个明确产出、能独立验证。有依赖的排串行；**独立的
  失败/子系统才并行**，一域一个执行者 —— 判据是互不相关、无共享状态、不会改同一
  个文件；修一个可能顺带修好另一个的，别并行。
- 派出去的每个任务要**自包含**：具体范围（哪一个文件/哪一段）、明确目标、约束
  （"只改这个脚本，不要重构其他部分"）、**要求返回什么**（根因 + 改动摘要）。
  笼统的"把测试修好"会让执行者跑偏。
- 写计划时把**任务的完整文本**给执行者，而不是丢一句"去看计划文件"——让他读完
  计划再找上下文本身就是浪费。
- 回来之后：读摘要 → 检查有无互相冲突的改动 → 合起来整体跑一遍。

### 7.2 每个任务两道审查（顺序不能反）

1. **规格符合性审查**：和要求的范围一致吗？有没有少做（缺功能）？**有没有多做
   （加了没要求的开关、参数）？** 多做了也算不合格。
2. **质量审查**：实现是否干净、有没有魔数、命名是否清楚、错误处理是否到位。

**规格没通过就不要进质量审查**。审查发现问题 → 由原执行者修 → **重新审查**，
不要跳过复审。结论按严重度分组（阻断 / 重要 / 次要）。

### 7.3 一条好技能/规则长什么样

**核心公式**：

> 好技能 = 专家知识 − 模型已经知道的东西

模型已经会的（循环怎么写、CSV 怎么读、什么是 p 值、通用的"注意错误处理"）写进
技能就是纯浪费 token；技能的价值全在**知识增量**上：非显然的决策树、"什么时候
A 比 B 好因为 C"的取舍、踩过坑才知道的边界情况、带原因的**绝对禁忌清单**。

- **`description` 只写"什么时候用"，绝不总结"怎么做"。** 被验证过的坑：描述里
  一旦概括了流程，模型会照着描述走而不读正文（描述写"任务间做代码审查"，结果只
  审了一次，正文写的是两次）。触发条件要写足关键词（工具名、扩展名、症状、报错）。
- **渐进披露**：元数据（名称+描述，始终在上下文）→ 正文（触发后加载，500 行
  以内）→ 附属文件（`references/` 资料、`scripts/` 代码、`assets/` 模板，按需
  加载）。正文里明确写"做 X 时必须完整读某个参考文件"和"做 Y 时别读它"。
- **自由度匹配脆弱度**：创意类给高自由度（文字指令）；有既定模式给中（伪代码 +
  参数）；格式敏感、错一个字节就毁文件的给低自由度（写死脚本，不许改）。
- **反模式清单最值钱**，每条带原因："不要用 jet/rainbow，它会在数据里造出假的
  结构"比"注意配色"有用一百倍。**控制篇幅**：常用技能 500 词以内。
- **验证方式**：先跑基线（没有技能时模型怎么做），记下它具体的错误做法，针对
  这些错误写规则，写完再跑一遍确认。没看过失败就写的技能，不知道教得对不对。

## 8. 一次任务的交付物清单

分析类任务收尾时，工作目录里应该有：

- [ ] `resources.json` —— 资源探测结果与据此做出的策略选择
- [ ] `<数据名>_eda_report.md` —— 探查报告，含结构、质量、下一步建议
- [ ] 分析脚本（可重跑；不要只在交互式环境里敲过一遍）
- [ ] 结果表 —— **全量表 + 显著子集**，CSV/TSV，列名自解释；需要复现的中间
      对象（拟合好的模型、归一化矩阵）一并落盘
- [ ] `figures/` —— 每张图给矢量（PDF/SVG）+ 300 dpi 位图（PNG），文件名说明
      内容，图注自解释
- [ ] `task_plan.md` / `progress.md` —— 做过什么、踩过什么坑
- [ ] 结论段落 —— 统计量 + 效应量 + CI + p 值 + 假设检验结果 + 局限性；
      只有显著结果没有效应量的结论不算完成
